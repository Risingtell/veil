Checks 2 to 4 run as simulations: a network node executes the contract for real and returns its actual result, without submitting a transaction. That is why no signing key is needed, and why a rejection here is the same rejection a submitted transaction would get.
01

The Merkle tree is maintained on-chain

Waiting

Reads leaf_count and root from the contract. There is no publish_root function: the contract hashed every deposit into this tree itself, using the same Poseidon parameters the circuit uses. So a root can only ever describe notes that were actually paid for, and no operator can invent one.

02

A real Groth16 proof, verified on-chain

Waiting

Sends a genuine Circom/snarkjs proof to verify_proof. The chain runs the BN254 pairing check in its own host function and returns the answer. This is the load-bearing step: the contract pays out nothing without it.

03

Redirecting a valid proof is rejected

Waiting

Takes that same valid proof and the same public inputs, unchanged, and asks the contract to pay a different address. This is exactly what anyone watching the network could attempt. The proof still verifies. The contract refuses anyway, because the payee is not the one the proof commits to.

04

Spending the note twice is rejected

Waiting

This note was already withdrawn in a real transaction. Replaying the proof against the correct recipient asks the contract to pay it out again.
